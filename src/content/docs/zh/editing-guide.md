这篇指南面向第一次参与官网内容维护的成员。目标不是教会你所有 Markdown 语法，而是让你能
独立完成一篇可发布的文章：文件放对位置、元信息写全、正文结构清楚、双语能对上、构建检查
通过。

> 不确定某一步时，先在本地改、先跑构建；不要把未验证的内容直接推到主分支。

## 先看清目录与命名

文章保存在 `src/content/docs/` 下，按语言分目录：

```text
src/content/docs/
├── zh/
│   ├── intro.md
│   ├── getting-started.md
│   └── ...
└── en/
    ├── intro.md
    ├── getting-started.md
    └── ...
```

规则：

- 中文放 `zh/`，英文放 `en/`；不要混放。
- 同一篇内容在两个目录下使用相同文件名。例如 `zh/editing-guide.md` 对应
  `en/editing-guide.md`。
- 文件名就是 URL 的一部分：`editing-guide.md` 对应 `/zh/docs/editing-guide`。已发布文章
  不要随意改名，否则旧链接会失效。
- 文件名使用小写英文、数字和连字符（kebab-case），不要用空格、中文或下划线。
- 一篇文章一个 `.md` 或 `.mdx` 文件；不要把多篇文章塞进同一个文件。

## Frontmatter 逐项说明

每篇文章开头必须有 frontmatter，用两条 `---` 包住：

```yaml
---
title: 文章标题
description: 一句话摘要，会出现在列表、搜索和分享卡片里
publishDate: 2026-10-17
category: news
tags: [官方公告]
image: /images/covers/example.webp
lang: zh
---
```

| 字段          | 必填 | 说明                                                                          |
| ------------- | ---- | ----------------------------------------------------------------------------- |
| `title`       | 是   | 文章标题。页面正文里不要再写一级标题。                                        |
| `description` | 否   | 建议写，40–80 字为宜；列表和搜索结果会用到。                                  |
| `publishDate` | 是   | 首次发布日期，格式 `YYYY-MM-DD`。修订不修改它。                               |
| `category`    | 否   | `news` / `project` / `studio`；不填表示官网与爱好者社区文章，进入对应标签页。 |
| `tags`        | 否   | 取自下方固定分类，可多选；不要自造新标签。                                    |
| `image`       | 否   | 封面路径。站内路径以 `/` 开头，或以 `http(s)://` 开头。                       |
| `lang`        | 否   | 可选兜底标识。实际语言由所在目录决定，不要靠它切换路由。                      |

### 日期与分类

- `publishDate` 写首次发布时间，不要写成“最后修改时间”。
- 新闻写 `category: news`；项目文章写 `project`，工作室文章写 `studio`；官网、社区、指南和
  维护说明不写 `category`，否则会进入新闻或项目/工作室标签页。
- 纠错、补链接、改排版不需要改日期；如果改动涉及事实，在文末加“修订说明”。

### 标签

标签是轻量分类，不是关键词堆。标签按标签页固定分组，一篇文章可选一个或多个最贴切的标签，
但不要自造新标签：

- **新闻资讯**：官方公告、活动、团队招募、募捐公示、合作事宜
- **官网与爱好者社区**：官网、社区、指南、运维、更新、团队招募
- **项目**：lkm-bot、科普计划、公益计划
- **工作室**：全链·技术服务工作室、星轨·全科家教工作室

### 封面图

如果提供 `image`，站内文件放在 `public/images/covers/`，并同时准备：

- `<name>.webp`：1200w 主图，用于文章页大图。
- `<name>-800w.webp`：800w 缩略图，用于列表与移动端。

frontmatter 只写主图路径：

```yaml
image: /images/covers/example.webp
```

组件会自动推导 `-800w` 缩略图。没有封面也可以发布，页面会使用标题生成的渐变占位，
不会出现空白。

## 正文结构

页面标题由 `title` 渲染成 `<h1>`，所以正文从二级标题开始：

```md
## 一级小节

正文段落。

### 更细的小节

- 列表项
- 列表项

> 需要强调的提示可以放在引用块里。
```

建议：

- 用二级标题（`##`）组织主要章节，三级（`###`）只用于确实需要拆分的小节。
  四级标题（`####`）也可以，但不要再深。
- 标题短而具体，能让人只看目录就知道这节讲什么。
- 一段只讲一个意思；长段落拆成两到三段。
- 列表用于步骤、并列项和检查项；不要把整篇文章写成列表。
- 代码、命令、frontmatter 用代码块，并标注语言。
- 表格适合字段说明和对照，不要让表格承担大段叙述。
- 文末可以加“相关阅读”或“延伸阅读”，链接到同语言的其它文章。

## 内链与外链

站内链接写完整路径，并带语言前缀：

```md
[快速上手](/zh/docs/getting-started)
[文章列表](/zh/news)
```

英文文章里对应改成 `/en/...`。不要写相对路径 `../getting-started`，站点路由变化时容易断。

外部链接优先使用官方或长期稳定的页面，并在链接文字里说明来源：

```md
[原始论文](https://example.org/paper)
```

不要只贴裸 URL；读者需要知道点进去会看到什么。引用外部结论时，尽量同时写明发布机构
与时间。

## 新建一篇文章

### 1. 选择 slug

用能概括主题的英文短语，例如 `editing-guide`、`summer-event-notes`。slug 一经发布就当作
稳定 URL，不要为了改标题而改名。

### 2. 创建中英文文件

在 `zh/` 和 `en/` 下各建一个同名文件。即使英文暂时没写完，也不要把中文内容复制过去占位；
要么等翻译完成再发布，要么先不发。

### 3. 填写 frontmatter

从上面的模板开始，至少确认 `title`、`description`、`publishDate`、`tags` 四项。新闻写
`category: news`，项目文章写 `project`，工作室文章写 `studio`。

### 4. 写正文并互链

先写清楚“为什么写、发生了什么、读者能带走什么”，再补背景和延伸阅读。文末链接到相关
文章，方便读者继续读。

### 5. 本地预览

首次参与先安装依赖：

```sh
pnpm install
pnpm dev
```

默认地址是 `http://127.0.0.1:4321`。打开：

- 中文：`http://127.0.0.1:4321/zh/docs/<slug>/`
- 英文：`http://127.0.0.1:4321/en/docs/<slug>/`

如果端口被占用，换一个：

```sh
pnpm dev -- --port 4322
```

在本地至少检查：

- 标题、摘要、日期、标签是否正确。
- 右侧目录是否列出了预期的二至四级标题。
- 中英文页面是否都能打开，文内链接是否落到正确语言。
- 移动端宽度下排版是否正常。
- 白天/夜间主题下文字与高亮是否可读。

### 6. 提交前检查

```sh
pnpm check
pnpm test
pnpm build
```

三条都通过再提交。`pnpm build` 会实际生成所有语言路由，能发现 frontmatter、图片路径和
链接之外的问题。

### 7. 提交与部署

用一句能看懂的话说明改了什么，例如：

```text
docs: expand getting-started and add editing guide
```

部署步骤见仓库根目录的 `DEPLOYMENT.md`。如果只是改内容，仍建议在合并前跑一次完整构建。

## 双语维护

双语不是逐字翻译，而是同一件事的两种清楚表达。建议：

- 先写一种语言，确认结构和事实，再翻译另一种。
- 标题、摘要、日期、标签保持语义一致；不要一边写“计划中”，另一边写“已确定”。
- 专有名词统一：理科迷 / PHIENTIST、七月团队 / July Team、活动策划部 /
  Event Planning Office。
- 中文用全角标点，英文用半角标点；不要把中文标点混进英文句子。
- 英文避免直译长句，优先用短句和主动语态。
- 两种语言的文内链接分别指向 `/zh/...` 与 `/en/...`，不要互相跳错语言。

## 修订与历史文章

- **纠错**：保留 `publishDate`，在文末加一段“修订说明”，写清改了什么、依据是什么。
- **补充**：如果只是补背景或后续进展，可以在原文增加小节，并标注“更新于 YYYY-MM-DD”。
- **改变结论**：如果新信息推翻了原文判断，优先新写一篇文章说明变化，再在旧文顶部加链接，
  而不是悄悄改掉旧结论。
- **历史新闻**：保留当时的语境和措辞，不为了统一宣传口径重写事件；需要补充后续时，
  用“后续”小节或新文章。

## 发布前检查清单

- [ ] 中英文文件同名，分别位于 `zh/` 与 `en/`。
- [ ] `title`、`description`、`publishDate` 完整，`category` 与所在标签页一致。
- [ ] 正文从 `##` 开始，标题层级没有跳级。
- [ ] 文内链接带正确语言前缀，点开不是 404。
- [ ] 没有“TODO”“待补”“占位”之类会出现在公开页面的文案。
- [ ] 封面与正文图片存在，路径以 `/` 开头。
- [ ] `pnpm check`、`pnpm test`、`pnpm build` 全部通过。
- [ ] 本地抽查中文与英文页面、移动端和夜间主题。

## 常见问题

**文章没有出现在 `/news` 列表？**  
检查 `category` 是否为预期的 `news`、`project` 或 `studio`，以及文件是否放在正确的语言目录下。
官网、社区、指南和维护说明不写 `category`，会进入「官网与爱好者社区」标签页。

**右侧目录是空的？**  
目录只收集正文中的二至四级标题。如果全文只有段落，或标题层级写成了 `#`，目录就不会有
内容。

**封面不显示？**  
检查 `image` 是否以 `/` 或 `http(s)://` 开头，文件是否真的在 `public/images/covers/`，
以及 800w 缩略图是否存在。

**构建失败？**  
先看报错指向哪个文件。常见原因是 `publishDate` 格式不对、`category` 拼写错误、缺少
`title`，或同一语言下出现重复 slug。

**英文页面里还有中文？**  
说明该段还没翻译，或误把中文文件复制到了 `en/`。发布前搜索一遍中文字符，确认没有遗漏。
